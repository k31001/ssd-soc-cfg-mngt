코드 옆에 사는 문서.
RTL을 진실로,
CI를 정합성으로.

Markdown · Git · Submodule · RTL-Grounded — 그것이면 충분하다.

Proposal · 2026 · soc-cfg-mngt
오프닝. "오늘은 우리가 어떻게 SoC 산출물을 AI 시대에 맞는 형태로 관리할지에 대한 제안입니다. 핵심 메시지는 단 한 줄. 모든 산출물은 마크다운, 모두 git, 문서 저장소는 submodule, RTL은 single source of truth, 정합성은 CI."
TL;DR — 한 장 요약

"문서가 코드 옆에 살고, AI가 그 문서를 직접 읽고,
CI가 그 정합성을 검사한다."

  • 3-repo: RTL · Doc · FW (단방향 submodule FW→Doc)
  • Markdown + Mermaid + WaveDrom · IP-XACT
  • 5종 문서 산출물 (HLD/DLD/PG/SFR/HAL.h)
  • RTL을 single source of truth로
  • FW + Python coverif on FPGA · Veloce · Zebu

배제한 것

  • Confluence · DOCX · PDF (정합성 검증 불가)
  • 단일 super-repo (권한 분리 곤란)

  • EDA 벤더 AI 락인

문제 정의 · 2 / 4

임베딩 RAG는 코드·SoC 도메인에서 무너진다

① 재인덱싱 오버헤드

RTL 변경 때마다 임베딩 갱신. 지연되면 LLM이 삭제된 함수를 호출하는 코드를 생성.

② 청킹 정합성 손실

IP-XACT XML, register map 표는 전체로서만 의미. 청크가 잘리면 환각.

③ 의미 유사도의 잡음

IRQ_EN과 INT_ENABLE은 의미적으로 유사 — 그러나 버그를 만든다.

"Most enterprise RAG failures stem from context quality, not retrieval recall." — Unblocked, "Context Engine vs RAG"
SLIDE 04 — RAG의 3대 약점
벡터DB의 약점 3가지를 카드로 명료하게. 인용은 RAG 업계 자체의 진단.

우리의 가설

RTL을 single source of truth로 두고,
모든 산출물은 그것의 그림자로 자동 동기화되며,
AI는 그 산출물을 결정론적으로 읽는다.

이 가설이 성립한다면, 4개 빌딩블록만 있으면 된다.

  • ① Markdown — git-friendly, diff 가능, AI 토큰 최효율
  • ② Git + Submodule — tag·branch 결정론적 버전, 권한 분리
  • ③ IEEE 1685-2022 IP-XACT — SFR의 국제 표준
  • ④ RTL-Grounded CI — invariant 검사로 정합성을 빌드 시스템에 위임
SLIDE 07 — 가설
문제에서 해답으로 넘어가는 슬라이드. 가설을 한 문장으로 압축하고, 4개 빌딩블록을 미리 보여줌. "이 4개는 새로 만들 게 아니라 이미 있는 것"이라는 점을 강조.

SLIDE 08 — 3-repo 아키텍처
핵심 관찰점: 1) 3개 저장소가 독립적이고 권한이 자연스럽게 분리됨. 2) Submodule은 한 방향 — FW → Doc. RTL은 submodule이 아니라 Doc CI가 fetch해서 참조. 3) 검증 플랫폼은 SV TB가 아니라 FPGA + Veloce/Zebu. Python이 펌웨어를 구동. 4) "어느 RTL × 어느 doc × 어느 FW로 측정했나"가 항상 한 줄로 확정됨.

③ FW Repo CI

어느 하나라도 깨지면 해당 저장소 PR이 자동 fail. 사람의 성실성에 의존하지 않는다. — 본 레포 tools/ipflow.py가 한 저장소 내에서 동일 invariant 체크를 실증 (irq_ctrl·trng 두 IP에서 PASS)
SLIDE 11 — D/F invariants
invariant가 두 저장소에 분리되는 게 핵심. Doc Repo는 RTL과 문서의 일치를, FW Repo는 그 문서(submodule)와 펌웨어·시나리오의 일치를 봄. "PR 시점에 자동 차단"이 본 제안의 가장 차별적 부분.
