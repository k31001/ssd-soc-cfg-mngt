문제 정의 · 2 / 4

임베딩 RAG는 코드·SoC 도메인에서 무너진다

① 재인덱싱 오버헤드

RTL 변경 때마다 임베딩 갱신. 지연되면 LLM이 삭제된 함수를 호출하는 코드를 생성.

② 청킹 정합성 손실

IP-XACT XML, register map 표는 전체로서만 의미. 청크가 잘리면 환각.

③ 의미 유사도의 잡음

IRQ_EN과 INT_ENABLE은 의미적으로 유사 — 그러나 버그를 만든다.

"Most enterprise RAG failures stem from context quality, not retrieval recall." — Unblocked, "Context Engine vs RAG"
SLIDE 04 — RAG의 3대 약점
벡터DB의 약점 3가지를 카드로 명료하게. 인용은 RAG 업계 자체의 진단.

우리의 가설

RTL을 single source of truth로 두고,
모든 산출물은 그것의 그림자로 자동 동기화되며,
AI는 그 산출물을 결정론적으로 읽는다.

이 가설이 성립한다면, 4개 빌딩블록만 있으면 된다.

  • ① Markdown — git-friendly, diff 가능, AI 토큰 최효율
  • ② Git + Submodule — tag·branch 결정론적 버전, 권한 분리
  • ③ IEEE 1685-2022 IP-XACT — SFR의 국제 표준
  • ④ RTL-Grounded CI — invariant 검사로 정합성을 빌드 시스템에 위임

SLIDE 08 — 4-repo 아키텍처
핵심 관찰점: 1) 4개 저장소 — RTL, Doc, FW(SoC 위에서 동작), Test(SSD Host에서 동작) 모두 독립. 2) Submodule fan-out — Doc → FW · Doc → Test. RTL은 어떤 곳의 submodule도 아님. 3) 검증 환경은 두 면 — FPGA/Veloce/Zebu (FW 실행) + SSD Host (Python 실행). PCIe/NVMe로 연결. 4) "rtl-v* × doc-v* × fw-v* × test-v*" 4-tuple로 어느 조합을 측정했는지 확정.

AI 컨텍스트 주입의 두 가지 방식

RAG/MCP vs Submodule 직접 read

RAG/MCP 방식

[질의]
   ↓
[Vector search]  top-k 청크 (수십)
   ↓
[LLM context]   무관·중복 청크 + 진짜 정보 일부
   ↓
[출력]   환각 위험 · 인접 IP와 혼동

Submodule 직접 read (FW Repo)

[질의]
   ↓
